# 07 C++异常处理

## 一、异常处理概述

### 1.1 什么是异常

程序在运行过程中，难免会遇到各种各样的意外情况：打开一个不存在的文件、向已经满的磁盘写入数据、对一个空指针解引用、数组下标越界……这些**运行时发生的、非预期的错误**，在编程术语中被称为**异常（Exception）**。

"异常"这个词本身就暗示了它的属性——它不是正常流程的一部分。正常的程序逻辑是从输入到输出的一条通路，而异常则是这条通路上突然出现的岔路。如果岔路不被妥善处理，程序就会崩溃；如果处理得当，程序就能从岔路上绕回来，继续正常运行，或者至少优雅地退出。

打个比方：你每天开车上班走的路线就是"正常流程"。某天路上发生了交通事故导致封路——这就是一个"异常"。你有几种选择：绕路而行（异常被处理）、停在原地等待直到路通（程序挂起）、或者干脆掉头回家（程序退出）。C++ 的异常处理机制，就是让你能够在代码中预设这些"绕路方案"。

### 1.2 为什么需要异常处理

在 C++ 引入异常机制之前，程序员主要依赖以下手段来应对错误：

**方式一：返回值错误码**

这是 C 语言中最常见的做法：函数通过返回值来报告成功或失败。

```cpp
int Divide(int a, int b, int &result) {
    if (b == 0) {
        return -1;  // 返回 -1 表示"除数为零"错误
    }
    result = a / b;
    return 0;  // 返回 0 表示成功
}

int main() {
    int result;
    int ret = Divide(10, 0, result);
    if (ret != 0) {
        // 处理错误...
    }
}
```

这种方式的缺陷非常明显：

- **返回值语义混淆**：返回值既可能代表计算结果，也可能代表错误码，阅读代码时很难一眼分辨。
- **逐层传递的负担**：如果 A 调用 B，B 调用 C，C 的某个错误必须经过 B 层层传递才能到达 A。每一层都必须写 `if` 判断，代码臃肿不堪。
- **构造函数无返回值**：构造函数的名字就是类名，根本没有返回值可用，错误码模式在此完全失效。

**方式二：全局错误标志（errno）**

C 标准库使用全局变量 `errno` 记录最近一次错误的类型：

```cpp
#include <cerrno>
#include <cmath>
#include <cstdio>

double result = sqrt(-1.0);  // 数学上的错误
if (errno == EDOM) {
    // 发生了定义域错误
}
```

问题是 `errno` 是一个全局变量，在多线程环境下极不可靠——线程 A 设置的 `errno` 可能被线程 B 覆盖。此外，调用者很容易忘记检查 `errno`，导致错误被无声地忽略。

**方式三：assert 断言**

```cpp
#include <cassert>

void SetAge(int age) {
    assert(age > 0 && age < 150);  // 条件不满足则直接终止程序
    // ...
}
```

`assert` 只在 Debug 模式下生效，Release 版本中会被完全移除。它适用于调试阶段捕获编程错误，但不能作为正式的错误处理手段——你总不能因为用户输入了一个负数就在生产环境中把程序崩掉。

**异常处理机制的优势**

C++ 的异常处理机制从根本上解决了以上问题：

| 对比维度 | 错误码/errno | 异常处理 |
|---------|-------------|---------|
| 错误传播 | 逐层手动传递 | 自动沿调用链向上传播 |
| 返回值语义 | 返回值与错误码混杂 | 返回值只代表正常结果 |
| 构造函数 | 无法返回错误码 | 构造函数可抛出异常 |
| 疏忽风险 | 容易忘记检查 | 未捕获的异常会导致终止，不会被忽略 |
| 错误信息 | 通常只有一个整数 | 可以携带任意类型的丰富信息 |

### 1.3 C++异常处理的三个关键字

C++ 的异常处理围绕三个关键字展开：

| 关键字 | 作用 | 角色比喻 |
|-------|------|---------|
| `try` | 划定一个"监控区"，其中的代码如果抛出异常，将被后续的 `catch` 捕获 | 雷达站——监控空域 |
| `throw` | 抛出一个异常对象，表示"这里出事了" | 信号弹——发出警报 |
| `catch` | 捕获并处理匹配类型的异常 | 消防队——处理险情 |

这三个关键字协同工作，构成了一套完整的"检测—报告—处理"机制。

## 二、异常处理的基本语法

### 2.1 try-catch 语句块

`try-catch` 是异常处理的核心结构，它的基本形态如下：

```cpp
try {
    // 可能抛出异常的代码
    // 这段代码受到"监控"
} catch (异常类型1 变量名) {
    // 处理类型1的异常
} catch (异常类型2 变量名) {
    // 处理类型2的异常
}
```

一个 `try` 块后面可以跟多个 `catch` 块，每个 `catch` 块负责处理一种特定类型的异常。这类似于电路中的多级保护：总闸跳了找总闸，分闸跳了找分闸，每一级处理自己管辖范围内的故障。

来看第一个完整的例子：

```cpp
#include <iostream>
using namespace std;

int Divide(int a, int b) {
    if (b == 0) {
        throw "除数不能为零！";  // 抛出异常
    }
    return a / b;
}

int main() {
    try {
        int result = Divide(10, 0);
        cout << "结果是：" << result << endl;
    } catch (const char* msg) {
        cout << "捕获到异常：" << msg << endl;
    }
    cout << "程序继续执行..." << endl;
    return 0;
}
```

运行输出：

```
捕获到异常：除数不能为零！
程序继续执行...
```

这个例子展示了异常处理的完整流程：

1. `try` 块中的 `Divide(10, 0)` 检测到除数为零，执行 `throw` 语句。
2. `throw` 语句执行后，函数 `Divide` 立即终止，不再执行后面的 `return`。
3. 控制流转到 `catch` 块，`msg` 接收抛出的字符串。
4. `catch` 块执行完毕后，程序继续执行 `catch` 后面的代码。

> **关键理解**：一旦 `throw` 被执行，从 `throw` 点到匹配的 `catch` 之间所有尚未执行完的代码都会被跳过。这是一种**非局部的控制流转移**（non-local control flow transfer），它打破了常规的顺序执行模式。

### 2.2 throw 语句

`throw` 的语法很简单：

```cpp
throw 表达式;
```

`throw` 后面的表达式可以是任意类型：基本类型、字符串、类对象、甚至是指针。`throw` 语句执行时，会创建该表达式的一个**副本**（copy），然后将这个副本传递给异常处理机制。原表达式所在的作用域即使已经销毁，`catch` 块中仍然能拿到一份完整的拷贝。

```cpp
// 抛出不同类型的异常
throw 42;                        // 抛出 int
throw "文件打开失败";              // 抛出 const char*
throw std::string("网络超时");    // 抛出 string 对象
throw FileNotFoundException();   // 抛出自定义异常对象
```

`throw` 可以出现在任何位置——函数内部、构造函数中、析构函数中（虽然强烈不推荐）、甚至 `catch` 块内部（重新抛出）。

### 2.3 异常的类型匹配规则

`catch` 块按照**出现的顺序**依次尝试匹配异常类型。匹配规则遵循 C++ 的类型转换规则，但有一个重要的限制：**只有隐式类型转换中的少数几种被允许**。

具体来说，`catch` 的匹配规则如下：

| 匹配方式 | 是否允许 | 示例 |
|---------|---------|------|
| 精确类型匹配 | ✅ | `throw 42;` → `catch(int)` |
| 派生类到基类 | ✅ | `throw Derived();` → `catch(Base&)` |
| 非 const 到 const | ✅ | `throw "hi";` → `catch(const char*)` |
| 数组到指针 | ✅ | `throw "hi";` → `catch(char*)` |
| 标准算术转换 | ❌ | `throw 42;` → `catch(double)` — 不匹配！ |
| 隐式构造函数转换 | ❌ | `throw "hi";` → `catch(string)` — 不匹配！ |

下面这个例子演示了类型匹配的严格性：

```cpp
#include <iostream>
using namespace std;

int main() {
    try {
        throw 42;  // 抛出 int 类型
    } catch (double d) {
        cout << "捕获到 double" << endl;  // 不会执行
    } catch (int i) {
        cout << "捕获到 int: " << i << endl;  // 会执行
    }
    return 0;
}
```

输出：

```
捕获到 int: 42
```

如果抛出的是 `int` 而第一个 `catch` 期待的是 `double`，它不会被匹配。即使 `int` 可以隐式转换为 `double`，异常匹配也不允许这种算术转换。

## 三、异常的抛出与捕获

### 3.1 抛出基本类型异常

最简单的异常形式是抛出一个基本类型或字符串：

```cpp
#include <iostream>
using namespace std;

int GetArrayElement(int arr[], int size, int index) {
    if (index < 0) {
        throw "索引不能为负数";
    }
    if (index >= size) {
        throw "索引超出数组范围";
    }
    return arr[index];
}

int main() {
    int data[5] = {10, 20, 30, 40, 50};

    try {
        cout << GetArrayElement(data, 5, 8) << endl;
    } catch (const char* msg) {
        cout << "错误：" << msg << endl;
    }

    try {
        cout << GetArrayElement(data, 5, -3) << endl;
    } catch (const char* msg) {
        cout << "错误：" << msg << endl;
    }

    return 0;
}
```

输出：

```
错误：索引超出数组范围
错误：索引不能为负数
```

基本类型异常虽然简单，但携带的信息太少——一个整数或者一个字符串说明不了多少问题。在实际项目中，更常见的做法是抛出一个**类对象**。

### 3.2 抛出类对象异常

使用类对象作为异常载体，可以在异常对象中装入丰富的信息：错误码、错误消息、发生错误的文件名和行号，甚至可以附带当时的上下文数据。

```cpp
#include <iostream>
#include <string>
#include <ctime>
using namespace std;

// 自定义异常类
class FileException {
private:
    string m_filename;
    string m_message;
    time_t m_timestamp;

public:
    FileException(const string& filename, const string& message)
        : m_filename(filename), m_message(message) {
        m_timestamp = time(NULL);
    }

    string GetFilename() const  { return m_filename; }
    string GetMessage() const   { return m_message; }
    time_t GetTimestamp() const { return m_timestamp; }

    string ToString() const {
        string result = "[文件异常]\n";
        result += "  文件名: " + m_filename + "\n";
        result += "  错误信息: " + m_message + "\n";
        result += "  发生时间: " + string(ctime(&m_timestamp));
        return result;
    }
};

void OpenConfigFile(const string& path) {
    // 模拟：如果文件不存在则抛出异常
    if (path.empty()) {
        throw FileException(path, "文件路径为空");
    }
    if (path == "notfound.cfg") {
        throw FileException(path, "文件不存在");
    }
    cout << "成功打开配置文件：" << path << endl;
}

int main() {
    try {
        OpenConfigFile("notfound.cfg");
    } catch (const FileException& e) {
        cout << e.ToString();
    }

    return 0;
}
```

输出：

```
[文件异常]
  文件名: notfound.cfg
  错误信息: 文件不存在
  发生时间: Fri Jun 20 14:30:00 2025
```

使用类对象作为异常的优势一目了然：异常不仅仅是"出错了"，它还回答了"哪里出错了""为什么出错""什么时候出错"等一系列问题。

### 3.3 多个catch块的匹配顺序

当一个 `try` 后面跟着多个 `catch` 时，**顺序至关重要**。异常对象会被依次与每个 `catch` 的参数类型进行匹配，命中第一个匹配成功者，后面的 `catch` 不再考虑。

在使用继承时，这个规则尤其需要警惕——**基类的 `catch` 必须放在派生类的 `catch` 之后**：

```cpp
#include <iostream>
using namespace std;

class AppException {
public:
    virtual const char* what() const {
        return "应用程序异常";
    }
};

class NetworkException : public AppException {
public:
    virtual const char* what() const {
        return "网络连接异常";
    }
};

class TimeoutException : public NetworkException {
public:
    virtual const char* what() const {
        return "网络连接超时";
    }
};

int main() {
    // 正确的顺序：派生类在前，基类在后
    try {
        throw TimeoutException();
    } catch (const TimeoutException& e) {
        cout << "TimeoutException: " << e.what() << endl;
    } catch (const NetworkException& e) {
        cout << "NetworkException: " << e.what() << endl;
    } catch (const AppException& e) {
        cout << "AppException: " << e.what() << endl;
    }

    return 0;
}
```

如果将 `catch (const AppException&)` 放在最前面，那么后面的 `catch (const NetworkException&)` 和 `catch (const TimeoutException&)` 就永远没有机会执行了——因为派生类对象可以隐式转换为基类引用，它总是会匹配到第一个基类的 `catch`。大多数编译器会对此发出警告。

### 3.4 catch(...) —— 捕获一切

`catch(...)` 是一个特殊的语法，三个点号表示"任意类型"。它能捕获任何 C++ 异常，无论类型是什么。通常将它放在 `catch` 链的最末端，作为一个"兜底"的安全网：

```cpp
try {
    // 可能抛出各种异常的代码
    DoSomethingRisky();
} catch (const FileException& e) {
    cout << "文件错误：" << e.GetMessage() << endl;
} catch (const NetworkException& e) {
    cout << "网络错误：" << e.what() << endl;
} catch (...) {
    cout << "发生了未知异常！" << endl;
    // 做一些清理工作后重新抛出
    throw;
}
```

`catch(...)` 有两个典型使用场景：

1. **作为最后的兜底处理**，确保没有任何异常能从本层泄漏出去。
2. **在重新抛出之前做资源清理**：捕获一切，记录日志或释放资源，然后用 `throw;`（不带参数）将原始异常重新抛出。

> **警告**：`catch(...)` 内部无法直接访问异常对象本身——你不知道它是什么类型。如果确实需要检查异常对象，只能在 `catch(...)` 中使用 `throw;` 重新抛出，让外层的具体类型 `catch` 来处理。

## 四、异常的传播机制

### 4.1 栈展开（Stack Unwinding）

当一个异常被抛出后，运行时系统会沿着函数调用链**反向**搜索匹配的 `catch` 块。在搜索过程中，每离开一个作用域，该作用域内所有已构造的局部对象都会被自动销毁（调用析构函数）。这个过程被称为**栈展开（Stack Unwinding）**。

下面这个例子清晰地展示了栈展开的过程：

```cpp
#include <iostream>
using namespace std;

class Tracker {
private:
    string m_name;
public:
    Tracker(const string& name) : m_name(name) {
        cout << "[构造] " << m_name << endl;
    }
    ~Tracker() {
        cout << "[析构] " << m_name << endl;
    }
};

void LevelC() {
    Tracker c("C");
    cout << "LevelC: 即将抛出异常..." << endl;
    throw runtime_error("在 LevelC 中发生错误");
}

void LevelB() {
    Tracker b("B");
    LevelC();
    cout << "LevelB: 这行不会被执行" << endl;
}

void LevelA() {
    Tracker a("A");
    try {
        LevelB();
    } catch (const runtime_error& e) {
        cout << "LevelA 捕获异常: " << e.what() << endl;
    }
}

int main() {
    cout << "=== 栈展开演示 ===" << endl;
    LevelA();
    cout << "=== 程序正常结束 ===" << endl;
    return 0;
}
```

输出：

```
=== 栈展开演示 ===
[构造] A
[构造] B
[构造] C
LevelC: 即将抛出异常...
[析构] C
[析构] B
LevelA 捕获异常: 在 LevelC 中发生错误
[析构] A
=== 程序正常结束 ===
```

注意析构的顺序：C 最先被析构，然后是 B，最后是 A。这与构造顺序完全相反（后进先出）。这确保了所有局部资源在异常传播过程中都被正确释放——不会因为异常而导致资源泄漏。

### 4.2 函数调用链中的异常传播

当异常被抛出后，如果当前函数没有 `try-catch` 包裹，异常会沿着调用链逐层向上传播，直到找到匹配的 `catch` 块。如果一直传到 `main` 函数都没有被捕获，程序会调用 `std::terminate()` 终止。

```cpp
#include <iostream>
using namespace std;

void DeepFunc3() {
    throw "深层异常";
}

void DeepFunc2() {
    DeepFunc3();  // 没有 try-catch，异常继续向上传播
}

void DeepFunc1() {
    DeepFunc2();  // 同样没有捕获
}

int main() {
    try {
        DeepFunc1();
    } catch (const char* msg) {
        cout << "在 main 中捕获：" << msg << endl;
    }
    return 0;
}
```

上例中异常在 `DeepFunc3` 中抛出，穿过 `DeepFunc2` 和 `DeepFunc1`，最终在 `main` 中被捕获。中间两层函数无需编写任何错误处理代码——这正是异常相比错误码的最大优势：**错误传播的自动化**。

### 4.3 异常与局部对象析构

栈展开保证了局部对象被正确析构，但这引出了一个关键问题：**析构函数中能不能也抛出异常？**

答案是：**绝对不要！** 原因如下：

假设一个异常已被抛出，栈展开正在进行中，析构函数正在逐个调用。此时如果某个析构函数又抛出了另一个异常，运行时系统就面临一个两难局面——它同时有两个活跃的异常需要处理。C++ 标准对此的处理方式简单粗暴：直接调用 `std::terminate()` 终止程序。

```cpp
#include <iostream>
using namespace std;

class BadDestructor {
public:
    ~BadDestructor() {
        throw "析构函数中的异常";  // 极其危险！
    }
};

int main() {
    try {
        BadDestructor obj;
        throw "正常异常";  // 第一个异常
        // obj 要析构 → 析构函数又抛出异常 → 程序终止！
    } catch (...) {
        cout << "这行永远执行不到" << endl;
    }
    return 0;
}
```

这个程序不会输出任何 `catch` 中的内容——它在栈展开过程中就因为双异常而直接终止了。

## 五、标准异常类体系

### 5.1 exception 基类

C++ 标准库在 `<exception>` 头文件中定义了一个名为 `std::exception` 的基类，所有标准异常都派生自它。它的定义大致如下：

```cpp
namespace std {
    class exception {
    public:
        exception() throw();
        exception(const exception&) throw();
        exception& operator=(const exception&) throw();
        virtual ~exception() throw();
        virtual const char* what() const throw();
    };
}
```

`what()` 是一个虚函数，返回一个 C 风格字符串，描述异常的信息。派生类可以重写 `what()` 来提供更具体的错误消息。

标准异常类的继承体系如下：

```
std::exception
├── std::bad_alloc          （new 分配失败）
├── std::bad_cast            （dynamic_cast 转换引用失败）
├── std::bad_typeid          （typeid 作用于空指针）
├── std::bad_exception       （违反异常规范）
├── std::logic_error         （逻辑错误——程序中的 bug）
│   ├── std::domain_error    （定义域错误）
│   ├── std::invalid_argument（无效参数）
│   ├── std::length_error    （长度错误）
│   └── std::out_of_range    （越界访问）
└── std::runtime_error       （运行时错误——外部因素）
    ├── std::range_error     （范围错误）
    ├── std::overflow_error  （算术上溢）
    └── std::underflow_error （算术下溢）
```

标准库将异常分为两大阵营：`logic_error` 和 `runtime_error`。这种分类体现了设计者的意图：

- **`logic_error`**：理论上可以被程序员事先避免的错误。比如对数组越界访问——如果你在编码时检查了边界，这类错误就不会发生。
- **`runtime_error`**：即便程序逻辑完全正确，在运行时仍可能发生的错误。比如文件不存在、网络超时——这些不是代码的 bug，而是外部环境出了问题。

### 5.2 常用标准异常类

**bad_alloc —— 内存分配失败**

`new` 操作符在无法分配足够内存时抛出 `std::bad_alloc`：

```cpp
#include <iostream>
#include <new>  // bad_alloc 在这里定义
using namespace std;

int main() {
    try {
        // 尝试分配一个巨大的数组
        int* p = new int[0x7FFFFFFF];  // 约 8GB
    } catch (const bad_alloc& e) {
        cout << "内存分配失败: " << e.what() << endl;
    }
    return 0;
}
```

输出可能是：

```
内存分配失败: bad allocation
```

**out_of_range —— 越界访问**

`std::vector` 的 `at()` 成员函数在索引越界时抛出 `std::out_of_range`：

```cpp
#include <iostream>
#include <vector>
#include <stdexcept>
using namespace std;

int main() {
    vector<int> v;
    v.push_back(10);
    v.push_back(20);

    try {
        cout << v.at(5) << endl;  // 索引 5 越界
    } catch (const out_of_range& e) {
        cout << "越界错误: " << e.what() << endl;
    }
    return 0;
}
```

> **注意**：`operator[]` 不抛出异常，只有 `at()` 会。这是两种设计哲学的体现：`operator[]` 追求性能（不检查边界），`at()` 追求安全（检查边界并以异常报告错误）。

**invalid_argument —— 无效参数**

当你向函数传递了不合逻辑的参数时，可以抛出 `std::invalid_argument`：

```cpp
#include <iostream>
#include <stdexcept>
#include <cmath>
using namespace std;

double SafeSqrt(double x) {
    if (x < 0) {
        throw invalid_argument("SafeSqrt: 参数不能为负数");
    }
    return sqrt(x);
}

int main() {
    try {
        double result = SafeSqrt(-5.0);
        cout << result << endl;
    } catch (const invalid_argument& e) {
        cout << "参数错误: " << e.what() << endl;
    }
    return 0;
}
```

### 5.3 自定义异常类

在实际项目中，仅仅依靠标准异常类往往不够。你需要创建自己的异常类来表达特定领域的错误。最规范的做法是从 `std::exception` 或其子类派生：

```cpp
#include <iostream>
#include <exception>
#include <string>
#include <sstream>
using namespace std;

// 从 runtime_error 派生——这属于运行时错误
class DatabaseException : public runtime_error {
private:
    int m_errorCode;
    string m_sqlStatement;

public:
    DatabaseException(const string& message, int errorCode,
                      const string& sql = "")
        : runtime_error(message)
        , m_errorCode(errorCode)
        , m_sqlStatement(sql) {}

    int GetErrorCode() const {
        return m_errorCode;
    }

    string GetSqlStatement() const {
        return m_sqlStatement;
    }

    // 重写 what() 提供更详细的错误信息
    const char* what() const throw() {
        // what() 返回缓冲区的指针，这里用静态线程局部存储简化
        // 实际项目中可能需要更完善的字符串管理
        return runtime_error::what();
    }

    // 提供完整的诊断信息
    string GetFullDescription() const {
        ostringstream oss;
        oss << "数据库错误 #" << m_errorCode << ": "
            << what();
        if (!m_sqlStatement.empty()) {
            oss << "\n  SQL: " << m_sqlStatement;
        }
        return oss.str();
    }
};

// 具体的数据异常子类型
class ConnectionFailedException : public DatabaseException {
public:
    ConnectionFailedException(const string& server, int port)
        : DatabaseException("连接数据库服务器失败", 1001) {
        // 可以在这里记录服务器和端口信息
    }
};

class QueryFailedException : public DatabaseException {
public:
    QueryFailedException(const string& sql, int errorCode)
        : DatabaseException("查询执行失败", errorCode, sql) {}
};

// 使用示例
void ExecuteQuery(const string& sql) {
    // 模拟连接失败
    throw QueryFailedException(sql, 5001);
}

int main() {
    try {
        ExecuteQuery("SELECT * FROM users");
    } catch (const QueryFailedException& e) {
        cout << e.GetFullDescription() << endl;
    } catch (const DatabaseException& e) {
        cout << e.GetFullDescription() << endl;
    } catch (const exception& e) {
        cout << "标准异常: " << e.what() << endl;
    }
    return 0;
}
```

输出：

```
数据库错误 #5001: 查询执行失败
  SQL: SELECT * FROM users
```

**设计自定义异常类的基本原则：**

1. **从标准异常类派生**：这保证了与标准库和其他库的互操作性。即使对方只知道 `std::exception`，也能用 `what()` 拿到基本的错误信息。
2. **携带上下文信息**：错误码、时间戳、相关的文件名、SQL语句——凡是能帮助调试的信息都值得放进异常对象。
3. **创建有意义的类型层次**：`DatabaseException` 下面可以有 `ConnectionFailedException`、`QueryFailedException`、`TransactionException` 等。类型本身就是信息——`catch` 块根据类型就能知道大致是哪里出了问题。
4. **考虑拷贝的安全性**：异常对象可能在栈展开过程中被拷贝多次，因此异常类应该保证拷贝操作不会再次抛出异常。

## 六、异常规范（Exception Specification）

### 6.1 throw() 异常规范

C++ 提供了一种语法来声明函数可能抛出哪些类型的异常——这被称为**异常规范（Exception Specification）**。它的语法是在函数声明的参数列表后面加上 `throw(类型列表)`：

```cpp
// 这个函数保证不抛出任何异常
void NoThrowFunc() throw();

// 这个函数可能抛出 int 或 const char* 类型的异常
void MightThrowFunc() throw(int, const char*);

// 这个函数可能抛出任意类型的异常（等同于不加异常规范）
void AnyThrowFunc();
```

异常规范是函数签名的一部分，也是函数与调用者之间的一份"契约"：

```cpp
#include <iostream>
using namespace std;

// 契约：这个函数最多抛出 int 或 const char*
int SafeOperation(int a, int b) throw(int, const char*) {
    if (b == 0) {
        throw "除数为零";  // 契约允许 const char*
    }
    if (a < 0 || b < 0) {
        throw -1;          // 契约允许 int
    }
    return a / b;
}

int main() {
    try {
        int result = SafeOperation(10, 0);
        cout << result << endl;
    } catch (const char* msg) {
        cout << "错误: " << msg << endl;
    } catch (int code) {
        cout << "错误码: " << code << endl;
    }
    return 0;
}
```

### 6.2 异常规范的使用与陷阱

异常规范看起来是一层很好的保护，但它在实践中存在几个严重的问题：

**问题一：编译期不检查，运行时才报错**

C++ 的异常规范不是在编译期强制检查的，而是在**运行时**验证。如果一个函数声明为 `throw(int)` 却在内部抛出了 `double`，编译器不会报错（最多给一个警告），但程序在运行时会调用 `std::unexpected()`，进而默认调用 `std::terminate()` 终止程序。

```cpp
void Func() throw(int) {
    throw 3.14;  // 违反异常规范，编译不报错，运行时程序终止！
}
```

**问题二：模板中难以使用**

模板函数无法提前知道类型参数 `T` 的操作会抛出什么异常，因此很难写出有意义的异常规范：

```cpp
template <typename T>
void Process(const T& data) throw(???) {  // 应该写什么？
    data.DoSomething();
}
```

**问题三：性能开销**

带有异常规范（非空）的函数在运行时需要额外的检查代码。如果函数确实抛出了一个不在规范内的异常，运行时系统需要调用 `std::unexpected()`。这些检查会带来不可忽视的性能开销。

**问题四：空异常规范 throw() 的误导**

`throw()` 表示"这个函数不抛出任何异常"。但如果函数体内部确实抛出了异常怎么办呢？同样，不是编译错误，而是运行时直接 `std::unexpected()` → `std::terminate()`。这意味着 `throw()` 并不像看上去那样是一个"安全网"——它更像是"如果这个函数抛了异常，就直接崩掉"。

```cpp
void CriticalSection() throw() {
    // 假设这里抛出了一个异常...
    throw "error";  // 不会传播，直接 terminate()
}
```

正因为这些缺陷，异常规范在实践中**很少被使用**。`throw()` 在一些极早期的 C++ 代码中可以见到，但大多数有经验的 C++ 程序员都避免使用非空的异常规范。

> **历史注记**：C++11 废弃了非空的异常规范语法（`throw(type1, type2)`），改为引入 `noexcept` 关键字。不过这是现代 C++ 的内容，不在此展开。

## 七、异常安全（Exception Safety）

### 7.1 异常安全的三个级别

在异常可能发生的环境中编写健壮的代码，有一个专门的术语叫做**异常安全（Exception Safety）**。C++ 社区普遍接受 David Abrahams 提出的三个异常安全级别：

| 级别 | 名称 | 保证内容 |
|------|------|---------|
| 基本保证（Basic Guarantee） | 不变量保持 | 异常发生后，对象仍然处于**合法但可能已改变**的状态。没有资源泄漏。 |
| 强保证（Strong Guarantee） | 提交或回滚 | 操作要么完全成功，要么在异常发生时**完全恢复到操作前的状态**。就像什么都没发生过。 |
| 不抛出保证（Nothrow Guarantee） | 绝不抛异常 | 该操作绝对不会抛出异常。 |

用一个银行转账的例子来理解这三个级别：

```cpp
#include <iostream>
using namespace std;

class Account {
private:
    double m_balance;
    string m_owner;

public:
    Account(const string& owner, double balance)
        : m_owner(owner), m_balance(balance) {}

    double GetBalance() const { return m_balance; }
    const string& GetOwner() const { return m_owner; }

    // 基本保证：如果扣款成功但存款失败，原账户的钱已经少了
    void TransferBasic(Account& to, double amount) {
        this->Withdraw(amount);  // 先扣款
        to.Deposit(amount);      // 再存款——如果这里抛异常，钱就"丢了"
    }

    // 强保证：要么双方都成功，要么都没变化
    void TransferStrong(Account& to, double amount) {
        to.Deposit(amount);      // 先存到目标账户
        try {
            this->Withdraw(amount);  // 再从源账户扣款
        } catch (...) {
            to.Withdraw(amount); // 扣款失败，把已存的钱退回来
            throw;               // 重新抛出，告诉调用者转账失败
        }
    }

private:
    void Withdraw(double amount) {
        if (amount > m_balance) {
            throw runtime_error("余额不足");
        }
        m_balance -= amount;
    }

    void Deposit(double amount) {
        if (amount <= 0) {
            throw invalid_argument("存款金额必须大于零");
        }
        m_balance += amount;
    }
};

int main() {
    Account alice("Alice", 1000.0);
    Account bob("Bob", 500.0);

    try {
        alice.TransferStrong(bob, 200.0);
        cout << "转账成功" << endl;
    } catch (const exception& e) {
        cout << "转账失败: " << e.what() << endl;
    }

    cout << "Alice: " << alice.GetBalance() << endl;
    cout << "Bob: " << bob.GetBalance() << endl;

    return 0;
}
```

在 `TransferStrong` 中，如果扣款失败，我们通过 `catch` 块将已存入目标账户的金额撤回，确保源账户和目标账户的状态都回到操作前。这就是**强异常安全保证**——要么全部完成，要么全部撤销。

### 7.2 RAII与异常安全

想要实现异常安全，最重要的一条原则是：**用对象管理资源**——也就是著名的 **RAII（Resource Acquisition Is Initialization）** 惯用法。

RAII 的核心理念很简单：**将资源的生命周期绑定到对象的生命周期**。资源在构造函数中获取，在析构函数中释放。由于栈展开保证了局部对象一定会被析构，资源就永远不会泄漏，无论是否发生异常。

```cpp
#include <iostream>
#include <cstdio>
using namespace std;

// RAII 封装 C 风格文件操作
class FileHandle {
private:
    FILE* m_file;

    // 禁止拷贝
    FileHandle(const FileHandle&);
    FileHandle& operator=(const FileHandle&);

public:
    explicit FileHandle(const char* path, const char* mode) {
        m_file = fopen(path, mode);
        if (m_file == NULL) {
            throw runtime_error(string("无法打开文件: ") + path);
        }
        cout << "[文件打开] " << path << endl;
    }

    ~FileHandle() {
        if (m_file != NULL) {
            fclose(m_file);
            cout << "[文件关闭]" << endl;
        }
    }

    FILE* Get() const { return m_file; }

    void Write(const string& text) {
        if (fputs(text.c_str(), m_file) == EOF) {
            throw runtime_error("文件写入失败");
        }
    }
};

// 没有 RAII：容易泄漏
void WithoutRAII() {
    FILE* f = fopen("test.txt", "w");
    DoSomethingRisky();  // 如果这里抛异常，fclose 永远不会被调用！
    fclose(f);
}

// 使用 RAII：异常安全
void WithRAII() {
    FileHandle file("test.txt", "w");
    DoSomethingRisky();  // 即使抛异常，file 的析构函数也会关闭文件
}

int main() {
    try {
        WithRAII();
    } catch (const exception& e) {
        cout << "异常: " << e.what() << endl;
    }
    // 无论是否发生异常，文件都已被正确关闭
    return 0;
}
```

在 `WithRAII` 中，如果 `DoSomethingRisky()` 抛出异常，栈展开会调用 `file` 的析构函数，而析构函数负责关闭文件。资源不会泄漏。

### 7.3 资源管理的最佳实践

下面的几条原则帮助你在异常环境中写出安全的代码：

**原则一：永远不要在裸指针上管理资源**

```cpp
// 错误：如果中间的代码抛出异常，p 永远不会被 delete
void BadFunction() {
    int* p = new int[1000];
    DoSomething();     // 可能抛异常
    DoSomethingElse(); // 可能抛异常
    delete[] p;
}

// 正确：用 RAII 包装
void GoodFunction() {
    std::vector<int> v(1000);  // vector 的析构函数保证释放内存
    DoSomething();
    DoSomethingElse();
}
```

**原则二：先改变临时对象，再swap**

当你需要修改一个已有对象的状态时，先在临时副本上操作，成功了再用 `swap` 替换。这样如果修改过程抛出异常，原对象毫发无伤：

```cpp
class StringList {
private:
    std::vector<std::string> m_data;

public:
    // 强异常安全保证的赋值操作符
    StringList& operator=(const StringList& other) {
        StringList temp(other);  // 先创建一个完整副本（可能抛异常）
        std::swap(m_data, temp.m_data);  // swap 不抛异常
        return *this;
    }  // temp 析构，带走旧数据
};
```

**原则三：让析构函数保持简单且不抛异常**

析构函数不应该执行可能失败的操作。如果析构函数必须调用一个可能失败的操作，用 `try-catch` 把它包起来，吞掉异常：

```cpp
class NetworkConnection {
public:
    ~NetworkConnection() {
        try {
            Disconnect();  // 断开连接可能失败（比如网络已经断了）
        } catch (...) {
            // 析构函数中吞掉所有异常
            // 可以在日志中记录，但绝不重新抛出
        }
    }
};
```

## 八、异常处理的性能与代价

### 8.1 异常处理的实现原理

理解异常处理的内部原理，有助于在性能和可靠性之间做出明智的权衡。

大多数 C++ 编译器采用**零开销模型（Zero-Cost Model）**来实现异常处理。这个名字有些误导——它并不是说异常处理没有开销，而是说**不抛出异常时几乎不产生运行时开销**。代价被转移到了异常实际发生的时候。

实现上，编译器会生成两张辅助表：

- **栈展开表（Unwind Table）**：记录了每个函数中哪些局部对象需要在栈展开时被析构，以及对应的析构函数地址。
- **异常处理表（Exception Handler Table）**：记录了每个 `try` 块的范围，以及对应的 `catch` 块的地址和期待的异常类型。

当 `throw` 被执行时，运行时系统的工作流程大致如下：

1. 获取被抛出异常对象的类型信息（通过 RTTI——运行时类型识别）。
2. 从当前函数开始，沿着调用栈逐帧向上搜索。
3. 对每一帧，查阅异常处理表，看是否有匹配的 `catch` 块。
4. 如果有，则查阅栈展开表，执行该帧中需要析构的局部对象的析构函数，然后跳转到 `catch` 块。
5. 如果一直搜索到栈顶（`main` 函数之外）都没找到，调用 `std::terminate()`。

这意味着：
- **正常路径（无异常）**：几乎零额外开销。
- **异常路径（抛出了异常）**：开销相当大——需要搜索表、匹配类型、调用一连串的析构函数。

### 8.2 异常 vs 错误码的选择

这是一个在 C++ 社区中长期争论的话题。下表总结了两种方式的适用场景：

| 场景 | 推荐方式 | 理由 |
|------|---------|------|
| 构造函数失败 | 异常 | 构造函数没有返回值 |
| `operator[]` 和赋值等操作符 | 异常 | 这些操作符通常有固定的返回类型 |
| 预计频繁发生的"软错误" | 错误码 | 异常的开销太大 |
| 极少发生的"硬错误" | 异常 | 不牺牲正常路径的性能 |
| 需要穿透多层函数调用 | 异常 | 自动传播 |
| 实时系统或禁止异常的嵌入式环境 | 错误码 | 异常的开销不可预测 |
| 析构函数 | 两者都不用 | 吞掉错误，绝不要从析构函数中抛出 |

一个务实的建议：**对于真正的"异常情况"——那些理论上不应该发生、一旦发生就需要上层介入的事情——使用异常。对于可以预期的、频繁发生的情况（比如用户输入了非法字符），使用普通的控制流（if/else、错误码）就足够了。**

## 九、常见陷阱与最佳实践

### 9.1 不要在析构函数中抛出异常

前面已经提到过这一点，但它实在太重要了，值得单独强调。

**规则：析构函数绝不应该抛出异常。**

如果你的析构函数需要执行一个可能失败的操作，有两种处理方式：

```cpp
class Resource {
public:
    ~Resource() {
        // 方式一：吞掉异常
        try {
            CleanupDangerousResource();
        } catch (...) {
            // 静静地吞掉，必要时记录日志
        }

        // 方式二：提供一个单独的释放函数，让调用者在析构之前主动调用
    }

    void Close() {
        CleanupDangerousResource();  // 可能抛出异常，由调用者处理
    }

private:
    void CleanupDangerousResource() {
        // 某些可能失败的操作
    }
};
```

方式二允许调用者在对象析构之前主动调用 `Close()`，此时如果有异常，调用者可以妥善处理。如果调用者忘了调用 `Close()`，析构函数中的 `try-catch` 是最后的防线。

### 9.2 按值抛出，按引用捕获

这是一个 C++ 异常处理中最重要的编码准则之一：

```cpp
throw MyException();          // 按值抛出（创建临时对象）

catch (const MyException& e)  // 按引用捕获
```

**为什么要按引用捕获？**

1. **避免对象切片（Object Slicing）**：如果按值捕获基类对象，派生类的额外信息会被切掉。

```cpp
class BaseException {};
class DerivedException : public BaseException {
    int extra_data;  // 按值捕获 BaseException 时，这个信息会丢失
};

try {
    throw DerivedException();
} catch (BaseException e) {    // 对象切片！
    // e 只是一个 BaseException，extra_data 丢失了
}

try {
    throw DerivedException();
} catch (const BaseException& e) {  // 引用捕获
    // e 绑定到原始的 DerivedException 对象，完整信息得以保留
}
```

2. **避免多余的拷贝**：按值捕获会创建异常对象的又一个副本，而按引用捕获不产生拷贝。

3. **支持多态**：只有通过引用（或指针）才能实现虚函数的多态行为。如果你在 `catch` 中调用 `what()`，按值捕获基类就只能是基类的 `what()`，按引用捕获则能正确调用派生类重写的 `what()`。

### 9.3 不要在构造函数中让异常"逃逸"

构造函数的作用是初始化对象。如果初始化失败，抛出异常是唯一合理的报告方式——因为你不可能返回一个"半成品"对象给调用者。

但是，如果构造函数中分配了资源，就需要格外小心：

```cpp
class Widget {
private:
    FileHandle* m_file;
    NetworkConnection* m_conn;

public:
    Widget(const string& configPath)
        : m_file(NULL), m_conn(NULL)  // 初始化指针为 NULL
    {
        m_file = new FileHandle(configPath.c_str(), "r");  // 第一步
        m_conn = new NetworkConnection("192.168.1.1");     // 如果这步抛异常...
        // m_file 永远不会被释放！
    }

    ~Widget() {
        delete m_file;   // 如果构造失败，m_file 可能还是 NULL
        delete m_conn;
    }
};
```

问题在于：如果构造函数抛出异常，对象的析构函数**不会被调用**——因为对象从未"活过"。但 `new FileHandle` 分配的资源已经存在了，没人去释放它。

解决方案同样是 RAII——使用智能指针或资源管理类：

```cpp
class Widget {
private:
    std::auto_ptr<FileHandle> m_file;  // auto_ptr 是 C++98 的智能指针
    std::auto_ptr<NetworkConnection> m_conn;

public:
    Widget(const string& configPath)
        : m_file(new FileHandle(configPath.c_str(), "r"))
        , m_conn(new NetworkConnection("192.168.1.1"))
    {
        // 如果 m_conn 的构造抛出异常，
        // 已经构造完成的 m_file 会被 auto_ptr 的析构函数自动释放
    }
};
```

> **注**：`std::auto_ptr` 是 C++98 中的智能指针，在现代 C++ 中已被 `std::unique_ptr` 取代。这里用它来说明 RAII 的思想而不涉及现代 C++ 的特性。

### 9.4 合理使用异常层次结构

设计异常类时，遵循"由一般到特殊"的层次原则：

```cpp
// 项目根异常
class MyAppException : public std::runtime_error {
public:
    explicit MyAppException(const string& msg) : runtime_error(msg) {}
};

// 各模块异常
class NetworkException : public MyAppException { /* ... */ };
class DatabaseException : public MyAppException { /* ... */ };
class ConfigException : public MyAppException { /* ... */ };

// 各模块的具体异常
class ConnectionTimeoutException : public NetworkException { /* ... */ };
class QuerySyntaxException : public DatabaseException { /* ... */ };
```

这样的层次结构让调用者可以在合适的抽象级别上捕获异常。高层代码如果只关心"有没有出问题"，可以直接捕获 `MyAppException&`；如果需要根据具体的错误类型采取不同措施，可以捕获更具体的异常类型。

### 9.5 使用重新抛出保留异常类型

在 `catch` 块中，使用不带参数的 `throw;` 可以重新抛出当前的异常对象，并且**保留其原始类型信息**：

```cpp
void OuterFunc() {
    try {
        InnerFunc();
    } catch (const std::exception& e) {
        cout << "OuterFunc 记录日志: " << e.what() << endl;
        throw;  // 重新抛出原始异常，保留类型
        // 不要写 throw e; ——那会创建副本并可能切片
    }
}
```

`throw;` 和 `throw e;` 的区别：

- `throw;` ——重新抛出同一个异常对象，保留原始类型（如果是派生类，接收方仍然能看到派生类）。
- `throw e;` ——创建 `e` 的一个副本（按 `e` 的静态类型），可能导致对象切片。

---

## 十、总结

C++ 的异常处理是一把双刃剑。用得好，代码清晰、健壮、易于维护；用得不好，资源泄漏、程序崩溃、调试困难。

回顾本文的核心要点：

| 要点 | 说明 |
|------|------|
| 基本语法 | `try` 划定监控范围，`throw` 发出异常信号，`catch` 处理异常 |
| 栈展开 | 异常传播过程中，局部对象按照构造相反的顺序自动析构 |
| 类型匹配 | `catch` 按出现顺序匹配，派生类必须放在基类前面，算术转换不被允许 |
| 按引用捕获 | 避免对象切片，保留多态行为，减少拷贝开销 |
| 标准异常类 | 以 `std::exception` 为根，分为 `logic_error` 和 `runtime_error` 两大分支 |
| 自定义异常 | 从标准异常类派生，携带丰富的上下文信息 |
| 异常规范 | `throw()` 声明不抛出异常，但非空异常规范在实践中存在诸多问题 |
| 异常安全 | 三个级别：基本保证、强保证、不抛出保证。RAII 是实现异常安全的核心手段 |
| 析构函数 | 绝对不要从中抛出异常 |
| 性能取舍 | 无异常时几乎零开销，异常发生时开销巨大。异常用于真正的意外情况 |

**一个朴素的判断标准**：当你在代码里写了一个异常处理块，问自己——"如果删掉这个 `try-catch`，程序发生这种错误时会怎样？" 如果答案是可以接受地崩溃（因为这种情况理论上不可能发生），那么这正是一个适合用异常来处理的场景。如果答案是必须优雅地处理（因为这是用户操作中的常见情况），那么用 `if/else` 和错误码也许更合适。

异常处理不是银弹，它只是 C++ 工具箱中一件威力强大但需要谨慎使用的工具。理解它的工作原理、优势和代价，你就能在合适的时刻让它发挥最大的价值。
